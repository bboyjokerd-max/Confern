## 4. 判定：**不通過**（但原因不是程式碼效率）

| 預算 | 門檻 | 實測 | 結果 |
|---|---|---|---|
| 總計時間 | < 10 ms | 平均 16.660 / 最大 18.217 ms | **不通過** |
| 記憶體增幅 | < 5 MB | 0.36 MB | **通過** |

**「通過／不通過」：不通過。**

理由（重要，這改變了設計結論的方向）：

1. **超過門檻的 16.6 ms 幾乎全部是抓螢幕，而且它不是 CPU 成本。**
   抓螢幕那一格平均 12.828 ms／最大 14.292 ms，但完整診斷（`--diagnose`）顯示：

   | 診斷 | 結果 |
   |---|---|
   | `BitBlt` 抓 16×16（256 px） | avg 16.76 ms |
   | `BitBlt` 抓 512×512（262144 px） | avg 16.56 ms |
   | 四個不同螢幕位置 | 16.53 – 16.65 ms |
   | `GetDC(NULL)` / `GetWindowDC(desktop)` / `BitBlt\|CAPTUREBLT` / GDI+ `CopyFromScreen` | 全部 16.64 – 16.72 ms |
   | 連續呼叫 4 次 `BitBlt` | 66.66 ms = **每次 16.67 ms** |
   | **`DwmFlush()` 單獨呼叫（不抓圖）** | **avg 16.678 ms** |
   | `DwmFlush()` 之後再 `BitBlt` | `BitBlt` 本身 16.667 ms |

   抓 256 px 與抓 262144 px **一樣貴**、換 API 完全沒差、連「只等合成器、不搬任何
   像素」的 `DwmFlush()` 本身就是 16.67 ms —— 而 16.67 ms 正好是 **60 Hz 的一個
   vblank**。結論：這台機器上任何從桌面讀像素的 GDI 路徑都會被**合成器的更新週期
   （60 Hz）綁住**，BitBlt 是在等下一個合成週期，不是在搬資料。這不是最佳化能解決的成本。

2. **應用程式自己掌控的部分（模糊＋合成）遠低於門檻：平均 3.894 ms、最大 5.700 ms。**
   這證明「自製可分離模糊 + 自己合成玻璃」這條技術路線本身完全可行，
   真正的限制在「抓螢幕」這一步。

3. 記憶體一項**通過**（0.33 MB，門檻 5 MB）。初版每次重配置 435 KB 模糊緩衝與
   Bitmap 時是 +6.77 MB（不通過），改成**長命資源重用**後降到 0.33 MB。

## 5. 過程中踩到的坑

### 5.1 最貴的一個：幾何係數表元素大小不一致，打穿 managed heap

`Glow`／`Veil` 一開始宣告成 `byte[CaptureSize*CaptureSize]`（1 byte/像素），
但所有 `Blend*` 函式是以 **4 byte/像素**（premultiplied BGRA）定址。
於是 `BlendDisc(glow, 330, ...)` 往一個 108,900 byte 的陣列寫到 **byte 435,599**。

症狀極具誤導性：

- `Precompute()` 本身**完全正常跑完**，還印得出「pack loop done」；
- 崩潰發生在**緊接著的第一次 `GC.Collect()`**，錯誤是
  `Fatal error. Internal CLR error. (0x80131506)`，堆疊只有 `System.GC._Collect`；
- 我一度以為凶手是「配置資源」或「unsafe 指標」本身，花了很久往錯的方向找。

教訓：
- **unsafe 指標運算的「元素大小」必須跟陣列宣告一致**，這種錯誤不會在寫入當下報錯，
  只會在下次 GC 時爆炸，而且會讓無辜的步驟看起來像凶手。
- 事後補了兩道防禦：`Precompute()` 開工前檢查每個表都 ≥ `size*size*4`，
  以及 `--minrepro` 最小重現模式（只做「烘表 → GC」，不碰任何其他階段）。
  這個最小重現就是最後定位到問題的關鍵工具。

### 5.2 扇形消失：`atan2` 的角度範圍

`Math.Atan2` 回傳 [-180,180]，但扇區是以「正上方起算、順時針」表示
（`StartDeg = -90`），範圍本身也會跨過 0°。踩了兩層：

1. 直接 `deg >= a0 && deg <= a1`：第三個扇區回報成負角，**整格消失**（實測是暗玻璃色）。
2. 只把兩端各自正規化也不夠：第一個扇區是 `272.5°..357.5°` 再接 `0°..27.5°`，
   正規化後變成 `lo=272.5 > hi=27.5` 的空區間，**換成第一格消失**。

正解：不要比絕對角。改成 `Norm360(pixelDeg - a0Deg) > span` 才對。

### 5.3 扇區變成暗褐色：合成順序

第一版把 60 % 黑幕畫在扇區**之上**，整顆輪盤變成 `#302A25` 的暗褐，
與 `wheel-format-stable.jpg` 的亮奶油扇區完全不像。
扇區必須疊在**已經壓暗的背景之上**（而且要在同一條逐像素迴圈裡處理，
不能當成兩張圖先後 `DrawImage`，否則 alpha 會變成 `1 - (1-f)(1-ca)`
而不是規格要的「奶油 + 剩下的暗背景」）。

### 5.4 柔光暈洗掉整個盤面

光暈原本用同心圓疊滿 `Rw+39` 的範圍，等於在整個圓盤上鋪了一層 45 % 暖橘。
它把奶油扇區從 `#D6BEA8` 染成 `#31363F`（暗藍灰），視覺上完全認不出是奶油。
修法：光暈只留在**圓盤外緣**（`inDisc` 遮罩），不洗進盤面。

### 5.5 規格的 veil 55–65 % 與「看起來像奶油毛玻璃」在數學上衝突

這條是本次 spike 最重要的設計發現：

- 按規格 `veil=60%` 配 `cream=84%`，奶油色會被 60 % 黑幕壓成 `#31363F` 這類暗色。
  實測 60 / 45 / 30 / 18 % 四組，視覺模型對 60 % 的評語是
  「dark opaque disc with no glass character at all」。
- 扇區不透明度掃 80 / 65 / 52 / 40 %：80 % 桌布完全不透（像貼紙）、
  40 % 奶油色被洗掉，**52 % 是唯一同時「透出桌布」又「保住奶油色」的點**。
- 目前預設值是 `veil=22%`、`cream alpha=52%`、光暈不內溢，
  **刻意偏離題目給的 55–65 % 規格**，理由是照規格填數學上做不出奶油毛玻璃。
  這一項需要設計端拍板：要嘛改規格，要嘛接受「深色煙燻玻璃」而不是奶油玻璃。

### 5.6 其他

- **BitBlt 不會寫 alpha**：螢幕 DC 沒有 alpha 通道，抓完之後 DIB 的 alpha
  byte 內容未定義，必須自己全部填 255 才能做 premultiplied 合成。
- **模糊暫存區必須是整張圖大小**：`BoxBlurHorizontal` 用
  `Buffer.BlockCopy(scratch, 0, buf, row*stride, stride)` 寫回，一開始只配一列
  的長度就直接 `IndexOutOfRangeException`。
- **每帧重新配置資源會吃記憶體**：435 KB 模糊緩衝 + 一張 Bitmap，
  50 次就讓工作集漲 6.77 MB。改成建構時配置一次、每帧重用後降到 0.33 MB。
- **`Math.Atan2`／`sqrt` 不該出現在每帧的內圈**：把靜態幾何烘成係數表之後，
  合成從 4.3 ms 降到 0.69 ms。
- **不要用 PowerShell 改原始碼檔**：`(Get-Content -Raw) -replace ... | Set-Content`
  會把 CRLF 轉成 LF 並加上 BOM，直接把檔案弄壞。用編輯工具。
- **文字反鋸齒要用灰階**：ClearType 是次像素渲染、不寫 alpha，
  畫在分層視窗的點陣圖上會出現黑邊。本 spike 用 `AntiAliasGridFit`。
- **存檔前不要壓成純色底**：第一版把 ARGB 壓到純色 `#202226` 再存 PNG，
  結果玻璃底下的桌布全被換成一片灰，圖**完全無法用來判斷像不像毛玻璃**
  （視覺模型直接判定「不透明實心圓盤」）。正確做法是拿**同一張抓下來的真實桌布**
  當底再疊輪盤；透明區則另外出一張棋盤格版本。
- **分層視窗不吃系統材質**：DWM 的亞克力／Mica 只對一般視窗生效，
  `WS_EX_LAYERED` + `UpdateLayeredWindow` 沒有東西可畫 —— 這就是整個 spike 的前提。
- **游標不在抓圖裡**：`GetDC(NULL)` 抓不到硬體游標（`GetCursorInfo` 確認
  `CURSOR_SHOWING`），所以毛玻璃底下不會有游標殘影。這對輪盤來說是好事。

## 6. 沒有驗證的事項（誠實清單）

1. **沒有在任何其他機器上量過。** 16.67 ms 這個下限是在**這一台**（60 Hz、
   RTX 4070 Ti SUPER、Windows 11 25H2）量到的。顯示器 120/144 Hz、
   或不同 GPU／驅動的機器是否也一樣，**未驗證**。
2. **沒有驗證「深色桌布 vs 淺色桌布」的可讀性。** 設計文件
   `docs/aegis/plans/2026-10-01-ui-redesign.md` §4 要求兩種桌布各測一次，
   本 spike 只在當下的桌布上測。
3. **沒有真的建立分層視窗。** 整個 spike 是合成進一張普通 `Bitmap`，
   **從未呼叫 `UpdateLayeredWindow`**。所以「premultiplied BGRA 餵給
   `UpdateLayeredWindow` 之後畫面是否正確」未經端到端驗證。
4. **沒有驗證 DRM／安全桌面下 BitBlt 失敗的行為**，也沒有實作設計文件提到的
   純色 fallback。
5. **沒有驗證多螢幕與 DPI 縮放**：只用了 `SM_*VIRTUALSCREEN` 做 clamp，
   高 DPI 下的座標換算與 330 px 框的實際涵蓋範圍未測。
6. **沒有驗證 50 次迴圈是否能代表正式情境。** 這個迴圈會連續抓同一個區域，
   與「拖曳開始時抓一次」的真實使用模式不同；正式情境可能更接近
   「單次 16.7 ms」而不是「每帧 16.7 ms」。
7. **扇區只有 3 格、標籤是 3 個英文字。** 正式的 2–4 格版面、
   中文／非 ASCII 標籤、以及真實的扇區角度都未測。
8. **「像不像毛玻璃」只有視覺模型的評語，沒有人眼確認。**
   視覺模型在不同版本給的分數從 3/10 到 7/10 都有，且對同一張圖
   前後判斷互相矛盾（一下說扇區不透明、一下說棋盤格有透出來），
   所以**視覺評價不可靠，必須由人眼定案**。
9. **沒有量 `UpdateLayeredWindow` 本身的成本**（每帧把 330×330 推上螢幕的代價）。
10. **沒有量在真實拖曳手勢中，這 16.7 ms 是否會被使用者察覺。**
    設計文件的輪盤預算是 100 ms，若 16.7 ms 只是一次性的、就完全在預算內；
    但若要求每帧更新毛玻璃，60 fps 就剛好被吃掉一整個 vblank。

## 7. 給設計端的建議

1. **技術路線可行，但要把抓螢幕移出關鍵路徑。**
   模糊＋合成合計 3.9 ms（最大 5.7 ms），遠低於 100 ms 輪盤預算。
   把「抓螢幕 → 模糊 → 合成」放到**拖曳開始時（或非同步）做一次**，
   輪盤顯示時直接用已備好的點陣圖，使用者完全感覺不到那 16.7 ms。
2. **不要嘗試每帧重抓螢幕做毛玻璃。** 受合成器 60 Hz 週期限制，
   每帧至少要付 16.67 ms，等於吃掉整個 vblank。
3. **veil 規格需要重新拍板**（見 5.5）：`55–65 %` 與奶油毛玻璃互斥。
4. **保留純色 fallback**：既然抓螢幕是全鏈路唯一的外部依賴
   （DRM／安全桌面會失敗），fallback 一定要做。
