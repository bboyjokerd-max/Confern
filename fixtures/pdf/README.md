# `merge-pdf` fixtures（工具 `merge-pdf` 的測資）

這一目錄是**進版控的測資**，因為使用者要能重現驗收。它們由
`tools/verify-m3d.ps1` 的 **S20** 直接引用（路徑由腳本從 repo 根目錄推導，不寫死絕對路徑）。

## ⚠ 測資的來源（誠實聲明，不可省略）

**`fx-a`／`fx-b`／`fx-c`／`fx-r` 是用 `PDFsharp` 自己產生的**
（`new PdfDocument()` → `AddPage` → `XGraphics` 畫色塊 → `Save`）。

這件事的兩個後果要一起說：

- ✅ **對「頁面物件搬移」這條路是有效測資**：它驗的是「開來源檔（`Import` 模式）→ 逐頁
  `AddPage` → 整批序列化 → 原子寫出」這一整條路，包含**頁序**、**每一頁自己的尺寸是否原樣
  保留**（不縮放、不 fit-to-page）、`/Rotate` 有沒有跟著走、以及**內容流有沒有跟著走**
  （逐頁雜湊比對）。這些環節壞掉，這些測資會紅。
- ❌ **不能拿它宣稱「對真實世界 PDF 的相容性」**：產生器與被測程式是**同一套函式庫**，
  等於考題與解答出自同一支筆。真實檔案的變數（xref stream、object stream、加密、
  `/Annots`、字型子集、線性化、破損修復、非 ASCII 檔名…）**幾乎都沒有出現在這裡**
  （唯一的例外是兩份**手寫**的負向測資，見下）。
  「使用者的 Canva 輸出／掃描器輸出／Word 匯出讀不讀得動」是**未實測**的，
  任何人都不該用這份測資回答那個問題。

負向測資（`fx-broken*.pdf`）是**手寫位元組**、不是 PDFsharp 產生的，所以它們的壞法
是「別人寫的壞」，不受上面那條限制——但相對地，它們只代表**兩種**壞法。

## 已知的期望值（斷言用；由 `--merge-pdf-inspect` 實測）

每一頁的尺寸都**刻意不同**：合併的產物是一個二進位檔，而「第 3 頁是不是 `fx-c` 的第 2 頁」
只能從**每一頁自己的幾何**看出來。所以「尺寸序列」就是頁序的客觀證據。

| 檔案 | 頁數 | 逐頁尺寸（point） | 逐頁 `/Rotate` | 逐頁內容流長度 / sha256 前 12 碼 |
| --- | --- | --- | --- | --- |
| `fx-a.pdf` | 2 | 200×300, 210×310 | 0, 0 | 74 / `9102714aeeb4`, 80 / `2b2962f9ecba` |
| `fx-b.pdf` | 1 | 300×200 | 0 | 74 / `9afd975a8921` |
| `fx-c.pdf` | 3 | 100×100, 120×140, 160×180 | 0, 0, 0 | 73 / `4d17d32e24d6`, 80 / `2814e72c9603`, 78 / `711c279a7ae1` |
| `fx-r.pdf` | 1 | 300×200 | **90** | 74 / `9afd975a8921` |

`fx-a + fx-b + fx-c` 依序合併 ⇒ **6 頁**，尺寸序列
`200×300, 210×310, 300×200, 100×100, 120×140, 160×180`，**六個互不相同**。

### ⚠ `fx-b` 與 `fx-r` 的內容流雜湊**相同**（`9afd975a8921`）——這是刻意的

`/Rotate` 是頁面字典上的一個**屬性**，不是內容流的一部分，所以同一個尺寸、同一份繪圖
在旋轉 90° 之後，**內容流位元組完全一樣**。

這一對之所以要一起放進來，是因為它本身就是一條斷言：**「內容雜湊相同、但 `/Rotate` 不同」
必須能被分辨**。如果套件只比對內容雜湊，它會把 `fx-r` 當成 `fx-b`——而「旋轉被吃掉」
正是合併最容易犯、又最看不出來的錯（頁數對、尺寸對、內容也對，只有轉向不對）。
所以逐頁斷言**同時**比對 `size`、`rotate`、`sha` 三項。

### 負向測資

| 檔案 | 大小 | 產品看到的行為 | 為什麼它重要 |
| --- | --- | --- | --- |
| `fx-broken.pdf` | 84 bytes | `--merge-pdf-inspect` 讀不開；合併時在 **`PdfReader.Open (Import)`** 就失敗 | 它驗的是「**開不起來的檔**會被擋住」。⚠ 這**不是** fail-fast 最難的那一半——開檔就失敗很容易做對。 |
| `fx-broken-page-tree.pdf` | 2456 bytes | **開得起來**（`PageCount` 說 1 頁），碰到 `doc.Pages[0]` 才丟 `NullReferenceException` | **這才是 fail-fast 的重點**：它與 PDFsharp Issue #388 是同一個形狀——「開得起來、碰到頁面才炸」。任何「先用開檔成功或 `PageCount` 推論合得成」的實作都會在這裡漏掉。 |
| `fx-hybrid-xrefstm-onlystream.pdf` | 560 bytes | 開得起來且報 **0 頁** | 手寫的混合參照檔（傳統 xref 表 ＋ `/XRefStm` 指向 xref 串流，物件只被串流描述）。它驗的是「**開得了、但一頁都沒有**」要具名失敗——靜默跳過它會讓使用者拿到一個少了整份文件的合併檔，而且回報成功。 |

`fx-broken-page-tree.pdf` 的產生方式（**與 `fx-b.pdf` 同長度**，這是刻意的）：
把 `fx-b.pdf` 的 `/Kids` 裡第一個物件編號改成**位數相同但不存在**的編號（`4 0 R` → `9 0 R`）。
檔案長度不變、xref 位移仍然有效 ⇒ 開檔仍然成功，只有真的去碰那一頁才炸。

⚠ **`fx-broken.pdf` 走的是 `Open` 失敗那條路，所以它證明不了「AddPage 失敗也要整批放棄」。**
套件的 fail-fast 斷言**兩個都要用**：只測 `fx-broken.pdf` 會讓「把 AddPage 的失敗改成
記錄一則警告再繼續」這種反向演練**測不出來**（開檔就死了，根本到不了 AddPage）。

## 產生器

產生器**不在 repo 裡**（與本專案既有的測資慣例一致：`verify-m3d.ps1` 的
`New-FixturePng` 也是當場產生，不進版控）。它是一個一次性的 `net8.0-windows`
主控台專案，跑在 repo 之外（`%TEMP%\mkpdf`），內容是：

1. 依上表的尺寸逐頁 `AddPage` ＋ `page.Width/Height = XUnit.FromPoint(...)`；
2. `XGraphics.FromPdfPage` 畫兩個色塊（**每頁顏色與第二個色塊的寬度都不同** ⇒ 每一頁的
   內容流位元組都不同）。⚠ **刻意不畫文字**：畫文字會內嵌字型，讓每一份 fixture 從
   ~2.5 KB 變成 ~29 KB；
3. `fx-r` 額外設 `page.Rotate = 90`；
4. `fx-broken.pdf`：手寫一段**截斷**的 PDF 位元組（只有檔頭、一個物件與 trailer，沒有 xref）；
5. `fx-broken-page-tree.pdf`：讀 `fx-b.pdf`（Latin-1 逐位元組往返），用 regex 找到 `/Kids`
   裡第一個 `N 0 R`，把 `N` 換成另一個**位數相同**的數字再寫出（長度不變）；
6. `fx-hybrid-xrefstm-onlystream.pdf`：手寫，物件只由 `/XRefStm` 指向的 xref 串流描述。

### ⚠ 可重現性（誠實測量，不可省略）

**PDFsharp 產生的 fixture 逐位元組不可重現。** 實測兩次執行（間隔 2 秒）的結果：

| 檔案 | 大小兩次相同？ | sha256 兩次相同？ |
| --- | --- | --- |
| `fx-a` / `fx-b` / `fx-c` / `fx-r` / `fx-broken-page-tree.pdf` | 是 | **否** |
| `fx-broken.pdf`（手寫） | 是 | **是** |
| `fx-hybrid-xrefstm-onlystream.pdf`（手寫） | 是 | **是** |

差異來源（實測定位到第一個不同的位元組）：`/CreationDate(D:20261007170955+08'00')`、
XMP 的 `CreateDate`、以及 `xmpMM:DocumentID uuid:<每次都不同>`。
把時間戳與 UUID 正規化之後，`fx-a/b/c` 逐位元組相同 ⇒ **差異只有那些欄位**，
而**頁數、尺寸、內容流位元組全部一樣**（上面那張表的 sha 在兩次執行都相同）。

所以驗收的立場是：**不可以**用 fixture 檔案的 sha256 當期望值（它會變），
而**可以**用 `--merge-pdf-inspect` 印出來的頁數／尺寸／旋轉／內容流雜湊當期望值
（它們是內容的函數，不含時間戳）。

要重新產生：把上面六件事寫成一支小程式，輸出檔名與尺寸照上表即可。
**產生的檔案不必逐位元組相同**（同上的理由），但
`--merge-pdf-inspect` 的輸出必須與上表逐項相同。

## ⚠ 交付時必須對使用者說明的行為（實測）

1. **合併後的檔案不會保留書籤。** 實測：來源檔 `/Outlines`=True、合併後 `/Outlines`=False。
   PDF 的大綱（書籤）不會被複製過去。這一條已同步寫在工具說明的註解裡。
2. **含 `/XRefStm` 的 PDF 可能開得起來卻合併不了**（PDFsharp Issue #388，6.2.4 與
   7.0.0-preview-1 都未修；Canva 的輸出就是其中一例）。產品此時的行為是**整批不產出並
   指名那個檔**，不是產生一個殘缺的檔。
3. **需要密碼的 PDF** 會得到獨立的一句訊息（「這個 PDF 需要密碼才能開啟，請先解除密碼再
   合併」）：本工具**沒有**取得密碼的介面，所以使用者要做的是先解除密碼再回來。
4. xref stream 讀得進來、但輸出是攤平後的傳統 xref 表（**檔案可能變大**）；
   object stream 讀得進來、但不會寫出；`/Annots`（註解／表單）預設不做深拷貝。
