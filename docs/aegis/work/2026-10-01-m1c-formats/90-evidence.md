## 1. 本片的核心命題

> **能力不是宣告的，是探測出來的。**

`StubFormatCatalog` 把 `WEBP` 硬寫在目標清單裡，而這台機器**沒有 WebP 編碼器**——
那是假承諾：使用者選了才失敗，正是規格 §7.2 明列的缺陷。
本片把「可輸出的格式」改成實測集合，做不到的**不出現扇區**。

## 2. 實測結果（`--codecs`，2026-10-01 17:34）

| 格式 | 解碼 | 編碼 | 怎麼量到的 |
|------|------|------|------------|
| PNG | ✅ | ✅ | 2×2 點陣圖編碼 → 自產位元組解回（127 B / 1 frame） |
| JPG | ✅ | ✅ | 同上（633 B，品質 85） |
| BMP | ✅ | ✅ | 同上（70 B） |
| TIF | ✅ | ✅ | 同上（246 B） |
| GIF | ✅ | ✅ | 同上（49 B） |
| WEBP | **逐檔** | ❌ | 真檔 `new-comfyui-logo-icon-….webp` → **解出 2816×2816**；編碼無 libwebp |
| HEIC | **逐檔** | ❌ | 規格 §6.3：取決於系統 HEIF 擴充（本機 `heifExtension=installed`） |

編碼集合＝`[PNG,JPG,BMP,TIF,GIF]`，**正好等於量到的那些**（多一個就是假承諾，少一個代表探測有問題）。

## 3. 量測推翻了兩個我原本的「合理猜測」

這兩件事若照猜測寫下去，都不會有任何測試抓到——因為它們錯在**沒有人會去質疑的預設值**。

| # | 我原本的假設 | 實測真相 | 若沒量的後果 |
|---|--------------|----------|--------------|
| 1 | 「這台機器沒有 WebP 編解碼器」→ 宣告 `decode=no` | **WIC 解得出真 WebP（2816×2816）** | 使用者拖入 WebP 時被判「不支援的格式」，但其實可以轉 → 規格 §6.1 的功能白白少掉 |
| 2 | 「找不到解碼器」＝`COMException 0x88982F50`（`WINCODEC_ERR_COMPONENTNOTFOUND`） | 實際拋 **`NotSupportedException: No imaging component suitable…`** | HEIC 會顯示「不支援的格式」，而 §6.3 要求「需要 HEIF 影像擴充」＋「開啟 Microsoft Store」——**同一條路徑上兩個完全不同的處置** |

⇒ 因此能力改成**三態**（`Yes`／`PerFile`／`No`）：在還沒有檔案時假裝能回答是或否，就是寫出「可量測地錯」的宣告。

## 4. 解碼失敗 → 使用者訊息的映射（全部實測，非文件抄寫）

| 樣本 | 實測 | 映射 | 對應 §7.1 訊息 |
|------|------|------|----------------|
| 真 JPG（266 KB） | `Ok 1080x2340 Bgr24` | Ok | — |
| 真 WebP（31 KB） | `Ok 2816x2816` | Ok | — |
| 不存在的路徑 | `Unreadable` | Unreadable | 「讀不到」 |
| 純文字改名 `.heic` | `NotSupportedException`，品牌盒**不符** | **Unsupported** | 「不支援的格式」 |
| 正確 HEIF 品牌盒但資料截斷 | `COMException 0xC00D36BE`，`heifBrand=heic` | **Corrupt** | 「`name.heic` 無法解碼」 |
| 真 JPG 截斷成前 400 B | `FileFormatException ← COMException 0x88982F61` | **Corrupt** | 「`name.jpg` 無法解碼」 |

兩個關鍵設計：

1. **HEIF 品牌盒嗅探**（只讀前 12 位元組，不載入整檔）：分辨「這是 HEIC 但系統沒有解碼器」
   （→ 需要擴充）與「這根本不是影像」（→ 不支援）。沒有它，一個改名成 `.heic` 的純文字檔
   會被誤報成「請安裝 HEIF 擴充」。
2. **`0xC00D36BE`／`WINCODEC_ERR_BADIMAGE`／`WINCODEC_ERR_BADHEADER` → Corrupt**：
   「資料壞了」與「格式不支援」在 §7.1 是**不同的使用者訊息**，不可以混為一談。

## 5. 儀器誠實性

- **探測必須能回報失敗**：以保證不存在的路徑做反向對照，斷言必須得到 `Unreadable`——
  「永遠回報 Ok」的探測器會讓每個扇區都看起來可用，比沒有探測器更危險。
- `--codecs` 每一項都印出「怎麼量到的」（位元組數、frame 數、HRESULT、品牌），不是只有 PASS。
- 編碼集合的斷言是**正好等於**實測集合：日後真的打包 libwebp 時，這行必須連同能力一起改
  （不是自動適應——能力改變必須是有意識的決定）。

## 6. 尚未驗證（誠實列出）

| 項 | 為什麼沒驗 | 何時能驗 |
|----|-----------|----------|
| `NeedsExtension` 分支 | 本機**已安裝** HEIF 擴充，無法製造「有效 HEIC 但沒有解碼器」 | 在一台沒裝擴充的機器上（或使用者移除擴充後） |
| WebP 編碼 | 需要 libwebp（BSD），尚未打包 | M1f 打包階段；屆時 `encodable` 集合的斷言必須一起改 |
| 真實 HEIC 解碼 | 本機找不到任何 `.heic` 實檔 | 有實檔時用 `--codec-probe` 量一次即可 |

## 6b. C2–C5 落地後（同日）

`StubFormatCatalog` **已刪除**；輪盤與示範路徑都改走 `FormatCatalog`＋`CodecRegistry` 的實測能力。

驗證：**`tools/verify-m1c.ps1` S9 17/17**（新增跑者）。其中幾條值得單獨點名：

| 檢查 | 證明了什麼 |
|------|------------|
| S9.3 | 五個內建編碼器**真的** encode+decode 各跑一次（不是看它有沒有註冊） |
| S9.4 | 可輸出集合**正好**等於量到的集合（多一個＝假承諾；少一個＝探測壞了） |
| S9.5 | 探測**能回報失敗**（不存在路徑 → `Unreadable`）——永遠回 Ok 的探測器比沒有更危險 |
| S9.9 | 截斷的 PNG → `Corrupt`（不是「不支援」）：§7.1 對這兩者訊息不同 |
| S9.10 | 改名成 `.heic` 的純文字 → `Unsupported` 且**沒有** `heifBrand`：不會誤報「請安裝 HEIF 擴充」 |
| S9.11／S9.12 | 真 HEIF 品牌盒 → `heifBrand=heic`，且落在 `Corrupt`／`NeedsExtension` |
| S9.14 | 輪盤扇區＝**實測集合－原格式**（與 `--codecs` 交叉驗證，不是寫死清單） |

**成本量測（規格 §9.3 的 100 ms 預算）**：`codec catalog ready in 42.1 ms` 且在**啟動時**完成；
輪盤首次顯示仍是 **15.3 ms**——探測成本沒有滲進顯示路徑（這一點若做錯，只延遲數字是看不出原因的）。

**一個儀器缺口（自己造成、自己修掉）**：S9.13 原本在 `--codecs` 的日誌裡找 catalog 計時行，
但那條路徑根本不建 catalog → 那條檢查**永遠不可能失敗**。修法是量真正該量的地方
（輪盤路徑的日誌），並在 `--codecs` 補上 `codec probe cost` 行。這種「看起來有檢查」的空砲
比沒有檢查更糟，因此列在此處而不是悄悄修掉。

## 6c. 對 M1b 驗證的影響

S7 的兩條斷言原本把能力集合寫死（`targets=[PNG,WEBP,BMP,TIF]`、`select#1 target=WEBP`）。
若不改，它們會變成「記錄某一天的實作」而不是「驗證契約」。改法：

- **S7.16b**：扇區必須等於 `--codecs` 實測集合減去原格式（**跨儀器**交叉驗證）。
- **S7.18**：改成「選取前進到**第二個**扇區」，不論第二個是什麼。

### 換 catalog 時真的抓到一個退化

`-Section All` 第一次跑出 **49/50**：**S7.25「不同類別 → Mixed」失敗**。

原因是新的 `FormatCatalog` 對「不認得的副檔名」直接回 `Unsupported`，
於是 `[jpg, pdf]` 變成「不支援的格式」而不是「混合選取，請選同類別」——
**這正是 M1b 修過的同一個缺陷**（`StubFormatCatalog` 當時的 bug），被新實作重新引入。

修法與 stub 一致：**每一個不認得的副檔名各自成為一個類別**（`EXT:<ext>`），
所以兩個不同的未知副檔名仍是混合選取，而單一未知檔仍是「不支援的格式」。

修好後逐一實測分類語意（不靠跑者）：

| 選取 | 判定 | 使用者訊息 |
|------|------|------------|
| `[a.jpg, doc.pdf]` | Mixed | 混合選取，請選同類別 |
| `[doc.pdf]` | Unsupported | 不支援的格式 |
| `[a.pdf, b.pdf]` | Unsupported | 不支援的格式（同一個不支援類別，不是混合） |
| `[a.jpg, b.png]` | Ready，原格式 JPG | — |
| `[a.jpg, b.heic]` | Ready（同為圖片類別，§4.4 批次） | — |

> 這件事值得記下來：**驗證抓到的第一個 bug 是我自己剛寫的新程式碼**，
> 而且它錯在一個「已經修過一次」的語意上。若 S7.25 當初是寫死清單的斷言，
> 它就會在換 catalog 時一起被改壞，而這個退化會無聲通過。



## 7. 對 M1b 的影響（下一輪 C2 要處理）

`StubFormatCatalog` 的目標清單含 `WEBP`；真實能力集合**不含**。
C2 換上真 `FormatCatalog` 之後，`verify-m1b.ps1` 的 S7 斷言（`targets=[PNG,WEBP,BMP,TIF]`、
`payload select#1 target=WEBP`）必須改成**與 `--codecs` 實測交叉驗證**，而不是寫死清單——
否則那幾條檢查會變成「記錄某一天的實作」而不是「驗證契約」。
