# 修復清單：把稽核發現變成可執行的工作（2026-10-02）

來源：三份假故障稽核（289 個檢查 id，**REAL 162／WEAK 115／DEAD 12**）。

> **行號以 2026-10-02 的 HEAD 為準。** 修復若動到 app 端程式碼，後續引用同一份稽核的行號需要重新對齊——
> 稽核員自己也提醒過這一點（他們只能保證當下那一版的行號）。
原則：**先修「會讓人以為驗過、其實沒驗」的**，再修「永遠不會紅」的，最後才是命名與清理。
每一項都必須附「怎麼證明修好了」——修完要能用**假故障**證明它真的會紅。

## 這一輪真正要帶走的原則

**鐵律（「一條永遠不會失敗的檢查比沒有檢查更危險」）目前只被套用在少數幾條，沒有上升成 harness 的設計原則。**
每一支套件最後都應該有這樣一條斷言：

```
已註冊的檢查數 == 這個套件預期要跑的條數
```

少了它，任何一條檢查都可以在未來的重構裡**靜默消失**，而總結依然印「全綠」。
