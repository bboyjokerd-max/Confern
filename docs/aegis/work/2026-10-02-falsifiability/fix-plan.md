## 這一輪真正要帶走的原則

**鐵律（「一條永遠不會失敗的檢查比沒有檢查更危險」）目前只被套用在少數幾條，沒有上升成 harness 的設計原則。**
每一支套件最後都應該有這樣一條斷言：

```
已註冊的檢查數 == 這個套件預期要跑的條數
```

少了它，任何一條檢查都可以在未來的重構裡**靜默消失**，而總結依然印「全綠」。

還有一條同樣重要的慣例：**新檢查一律附加在最後，不得插入中間**。檢查 id 是被人引用一輩子的位址；2026-10-02 的 D3/D4 那片把 19 條新檢查插進 S16.24–S16.43，就把舊的 S16.24–S16.30 擠成了 S16.44–S16.50，使本文件與稽核文件裡那些編號**默默指到別的東西**。

### 仍未解的（不是這張表能結案的）

1. **26 條 inconclusive 需要真人輸入**：m1a 20 條、m1h 6 條（`-WithRealInput`）。它們不是假綠——它們誠實地說「沒驗到」——但也就代表那 26 個行為目前沒有任何自動證據。
2. **`verify-m1f.ps1` 是無 BOM 的 UTF-8（1674 個非 ASCII 位元組）**：PowerShell 5.1 會用 CP950 讀它，目前 CJK 只出現在註解裡所以還能跑；一旦有人在裡面加中文字串字面值，就會變成「莫名其妙的紅」。要嘛補 BOM，要嘛維持 ASCII-only（`verify-m3c/m3d` 有 BOM，是安全的那一邊）。
3. **假故障證明沒有全部留下腳本**：P0-2／P1-4 這一類「改 no-op 就會紅」的證明是當時手動做的，沒有可重跑的腳本。要讓它變成常設能力，得有一支 `tools\fault-inject.ps1`（目前不存在）。
