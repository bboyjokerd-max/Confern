## 0. 本片要解掉的一件事

現在 `StubFormatCatalog` 用**副檔名**猜格式，而且把 `WEBP` 硬寫在目標清單裡。
後者是一個**假承諾**：這台機器沒有 WebP 編碼器，選了會失敗——而「靜默失敗」是規格 §7.2 明列的缺陷。

> 本片的核心決策：**能力不是宣告的，是探測出來的。**
> 目標格式清單＝「這台機器上真的能編碼成功的格式」－原格式。
> 做不到的格式**不出現扇區**，而不是出現後才失敗。

## 1. 技術路線（由規格決定，不由我選）

§6.1／§6.2 兩張表都寫「自建（**WIC**）」。GDI+ 不是 WIC，而且 **GDI+ 用不到 WIC 編解碼器**——
系統的 HEIF 擴充註冊的是 WIC codec，所以 HEIC 輸入只有走 WIC 才可能成立。

⇒ 編解碼層用 `System.Windows.Media.Imaging`（WPF 的 WIC 包裝：`PngBitmapEncoder`／`JpegBitmapEncoder`／
`BmpBitmapEncoder`／`TiffBitmapEncoder`／`GifBitmapEncoder`／`BitmapDecoder`）。
`<UseWPF>true</UseWPF>` 與既有的 `<UseWindowsForms>true</UseWindowsForms>` 可並存，
參考組件在本機（`Microsoft.WindowsDesktop.App.Ref`），**不新增任何 NuGet 套件**（本機無全域快取，加了就離線還原失敗）。

**這不影響 D10**：輪盤仍然用 GDI+ 畫（D10 的否決理由是「WPF 需要自己的 Dispatcher 幫浦對抗現有 `GetMessage` 迴圈」）。
WIC 影像 API 不需要 Dispatcher；跨執行緒時一律 `Freeze()`。

## 4. 風險與對策

| 風險 | 對策 |
|------|------|
| 能力探測本身出錯 → 悄悄少掉扇區（比多一個扇區更危險） | 探測**真的編碼一次**並在 `--codecs` 留下逐項結果；任何一項失敗都必須在日誌中顯示原因 |
| `UseWPF` 導致離線還原失敗 | 不新增 `PackageReference`；建置後立刻確認 `dotnet build` 無還原錯誤 |
| 加入 WPF 影像 API 後啟動變慢 | 只在第一次需要時載入（探測延遲到第一次使用或 `--codecs`），並量測冷啟時間（§9.3 預算 1.5 s） |
| 探測結果被誤當「永久事實」 | 探測結果**不落地快取**；同一行程內快取，跨行程重新探測（使用者可能剛裝了擴充） |
