## 托盤與開機自動啟動（待辦 ④）做了什麼

- **托盤圖示**：用 Win32 `Shell_NotifyIcon` 實作，兩個尺寸的圖示都用 GDI+ 依凍結的調色盤**當場畫**——沒有素材檔、沒有新增套件。選單三項＝開啟設定／暫停轉換／結束；**雙擊＝開啟設定頁**（設定頁從此不必再靠旗標就進得去）。
- **開機自動啟動**：`HKCU\...\Run` 的唯一擁有者 `Autostart`。**只有常駐程式會套用它**；`--settings-set` 是純設定檔編輯器，永遠不碰 Run 機碼。
- **那個發現值得記下來**：規格的預設是「開機自動啟動＝開」，第一版接上去之後，**既有的驗收套件開始在你真正的 Run 機碼留下一筆 `Confern`**（指向 `bin\Release`）。這不是推論——是裝了登錄檔監看、逐秒抓出來是 `m1f --settings-ui-live` 與 `m1b --wheel-payload` 寫的。修法＝`--no-autostart`（三態：寫入／移除／完全不要碰），四支既有套件都帶上；殘留那筆已刪除，現在 m1g 會斷言「跑完一整輪，真實 Run 機碼與跑之前完全相同」。
- **我複核時修掉的安全回歸**（第一版真的出貨會出事）：托盤的「暫停」呼叫的是保險 #5 的 `OnKillSwitch()`，所以①日誌會印 `*** KILL SWITCH ***`（而 `m1a` 的 S3.8 正是在斷言那一行 ⇒ 那條斷言可以被「按一下托盤暫停」滿足）、②「繼續」無條件呼叫 `Resume()` ⇒ **按一下托盤就能解除緊急停用，與規格 §4.2.2「直到重啟」矛盾**、③托盤照「使用者的意圖」翻自己的提示文字 ⇒ 復原被拒絕時它會顯示 `running` 而捕捉其實是停用的。
  修法＝**狀態共用、復原的權力不共用**：托盤的暫停走新的 `Pause(why)`（可復原、不印 KILL SWITCH、不扣閂），`OnKillSwitch()` 才會扣下只進不退的閂，`Resume()` 遇到閂就**大聲拒絕**；托盤改成在回呼跑完後**去問真正的事實**（`try/finally`）。新增 `S15.24`／`S15.25` 兩條斷言，**它們在修改前的程式碼上會失敗**（我確認過失敗的樣子）。

### D1 的設計（讀完程式碼後定案）

`Program.cs:673` 顯示**藥丸早就用自己的 `VisualLayer` 實例**，不與輪盤共用（輪盤是 `Program.cs:670`
那個）。所以 D1 是**局部改動**：

- 抽出一個只有 6 個成員的小介面（`Show`／`Hide`／`IsVisible`／`Frames`／`StartTick`／`TickRequested`），
  由現有 `VisualLayer`（原封不動）與新的 `PillWindow` 共同實作 ⇒ `ProgressPresenter` 只依賴介面。

  `WS_EX_TRANSPARENT`（那正是目前穿透的原因）；`WM_LBUTTONUP` → `ToggleDetail()`、
  `WM_MOUSEACTIVATE` 回 `MA_NOACTIVATE`（不搶焦點）。
- **幾何仍然只有一份**：視窗位置＝`PillRect`，由 `ProgressPresenter` 決定，不另立第二份。
- 副作用是好的：有了真視窗，**D2 的「游標停在藥丸上」才第一次變成可觀測狀態**

### 狀態誠實聲明

### C3 的做法決定（下一輪照這個做）
原計畫 §10.3 寫的是「job 訊息加 `outputDir`、協議升到 3」。實作前重新想過，改採**命令列**
而不是 job 訊息，理由：
- 這個值是**每個 worker 行程一個**（設定檔不會在一批轉檔中途改變），不是「每個工作一個」——
  放進 job 訊息等於把常數當變數傳，而且逼著升協議版本（雙方必須同時換，風險比較大）。
- 命令列參數是 worker **啟動時**就固定的，語意更準確，也讓 `--worker` 自己就能被測試
  （不必先建立一個假的 job）。
- 代價：worker 多一個參數解析（`--output-dir <path>`）。仍然只有一個來源——UI 讀設定檔，
  再傳給它啟動的 worker；**不讓 worker 自己去讀設定檔**（那會變成兩個擁有者，設定檔中途改變
  時兩邊會看到不同的值）。

切片順序：① worker 接受 `--output-dir` 並傳進 `Convert`／`Rotate90`；② client 啟動 worker 時
帶上它（來源仍是 UI 的設定）；③ 輪盤上顯示目的地（與來源不同時顯示資料夾名，全路徑進日誌）；
④ 設定頁欄位；⑤ 套件斷言。

### 工具教訓（兩條，都踩過）
1. **PowerShell 5.1 會把多行字串按換行拆開**再傳給原生程式，所以 commit 訊息裡只要有一行以
   連字號開頭（例如 `--rotate90 ...`），git 就會把它當成選項並失敗。改用 `git commit -F <檔案>`。
2. 訊息檔用 `Set-Content -Encoding UTF8` 會**帶 BOM**（標題會多一個看不見的字元）。改用

## 2026-10-05（第七段）更正上一段：Shift 即時切層其實是**真的壞掉**，現已修好並有自動化證據

  我把它歸因於 harness，是我判斷錯誤——這一條要記著：**當一個功能怎麼測都測不出來時，
  下一個假設應該是「功能本身沒作用」，不是「我的工具爛」。**

修法（`3bfb44a`）：條件改成 `vk == VK_SHIFT || 0xA0 || 0xA1`，並新增
`--raise-with-hooks`（raise 的同時裝鉤子）與 `--wheel-layer-probe <png>`（唯一可自動化入口），

## 第八段（2026-10-06 上午）：修掉「設定頁關掉後再也開不回來」＋補上一直缺的可觀測性與覆蓋

使用者實測回報：「我測試隨便點了一下整個設定頁就消失了，再去左下角（托盤）按也叫不出來。」
這一條**真的有病**，而且舊的驗收完全照不到它。

### 根因（量到的，不是推論）

`Drain()` 跑在 `DispatcherTimer` 的回呼堆疊上，而佇列裡的工作可能是**阻塞的** `SettingsWindow.ShowDialog()`（巢狀 dispatcher 迴圈）。WPF 的 `DispatcherTimer` 是「回呼返回之後」才排下一次 tick（dotnet/wpf `DispatcherTimer.FireTick`：`if (Tick != null) Tick(...); if (_isEnabled) Restart();`），所以回呼一旦不返回，計時器就永遠不再 tick ⇒ `Pending` 再也沒人抽 ⇒ 之後每一次 `Open()` 的工作項都躺在佇列裡，`IsOpen` 停在 true、視窗永遠不出現。

為什麼「第一次開沒事、第二次必死」：第一次的 `Drain()` 是在 `Dispatcher.Run()` **之前**直接呼叫的，不在回呼堆疊上，所以 modal 迴圈裡的 tick 照常觸發；第二次是在 tick 回呼裡抽到那個阻塞工作，於是 tick 從那一行之後全部消失。

量到的證據（探針逐行記 tid／drainDepth／dialogDepth，收工前全部移除）：
- 阻塞後 25 ms 的 tick 應有約 200 行，實際 **0 行**；但 dispatcher 仍在抽訊息（`BeginInvoke` 在 `dialogDepth=1` 之下照樣跑完）⇒ **不是** UI 執行緒死掉。
- modal 迴圈一退出，tick 立刻大量恢復（正證）。
- 期間視窗其實是好的（`IsLoaded=True IsVisible=True 540x820`）⇒ 問題在「再也沒人把工作抽出來」，不在畫視窗。

⚠ 走過的彎路（四個被推翻的假設，值得記下來）：UI 執行緒死掉 ✗、兩個實例互相干擾 ✗（使用者單一實例下照樣重現）、擷取開始時產品主動關頁 ✗（常駐路徑沒有任何 `SettingsUi.Close()`）、托盤守衛擋住重開 ✗。⇒ 教訓：**當症狀完全量不到時，先假設是「功能真的壞了」，並且先問「有沒有任何測試真的走過這條路」。**

### 修法（最小一刀）

`src/Sidecar/Settings/SettingsUi.cs` 的 pump：回呼**只排**一次 `Drain` 後立刻返回
`(_, _) => dispatcher.BeginInvoke(DispatcherPriority.Normal, new Action(Drain))`。
擁有者是 pump 那一行（計時器回呼與阻塞工作耦合），`Drain()` 仍是唯一的抽乾實作。

### 同時補上兩件一直缺的東西

- **可觀測性**：設定頁執行緒的日誌佇列原本只在特定主迴圈抽乾，純托盤操作時**永遠不會**寫進日誌——使用者那一輪 `settings ui:` 的行數是 **0**，等於診斷全瞎。現在常駐路徑也會抽。
- **覆蓋**：`--settings-ui-selftest` 與 `--tray-selftest` 都**沒有**「關掉之後再開一次」這條，而且關窗走的是產品自己的 `SettingsUi.Close()`，不是使用者的方式（視窗自己的取消鈕）。現在兩者都補上，並新增「視窗真的存在」的檢查，用來區分「`IsOpen` 說開著」與「畫面真的在」。

- 反向驗證：把那一行改回去，兩支自測都**紅**——`reopened=True windowPresent=False ... the settings UI thread did not pick it up`；托盤 `FAIL the open-settings command opens the page AGAIN after it was closed`。改回後綠。
- `--settings-ui-selftest`：exit 0，`ok=True (… reopened=True windowPresent=True)`。
- `--tray-selftest`：exit 0，`checks=14 failed=0`（新增的那條是「關掉後托盤能再開」）。

### m1d 的 `S12.10i` 為什麼紅：它不是回歸，是**測試自己用了使用者的設定檔**

`S12.10i` 問的是「放手（mouse up）那條路徑轉出來的檔有沒有落地」，而它找檔的地方是**寫死的** `Split-Path -Parent $srcJpg`（＝`%TEMP%\m1d-verify`）。但同一支套件的 `S12.10a`–`S12.10i` 走的是 `--wheel-payload`，也就是**產品 UI 那條路**：輸出資料夾跟著 `Settings.OutputFolder`（規格 §9.5）走。而這幾條**沒有**傳 `--settings-file`，所以它繼承的是**使用者真的那一份** `%LOCALAPPDATA%\Confern\settings.json`。

```csharp
bool moveCanChange = _imageWidth - _rect.Width > 0 || _imageHeight - _rect.Height > 0;   // 修後
```

`moveCanChange` 問的是「**有沒有任何一個方向可以動**」，但寫成 `&&`（寬有餘 **且** 高有餘）之後，**只要任一邊貼齊影像邊界就是 false**，框內拖曳於是被歸成 `DragMode.New`＝**把整個框清掉重畫**。這正是他說的「變成重畫，要從頭來」。

⚠ **「貼齊一邊」不是邊緣情形，是常見狀態**：直式照片按 16:9／4:3 之後框寬就等於圖寬（`CropMath` 取的是框內**最大等比矩形**，直式圖上一定貼齊左右）。

⚠ 而且**那個條件的註解本來就寫著**「滿寬的橫帶在垂直方向仍然搬得動（上界 > 0），必須繼續是 Move」。**註解是對的，程式碼與它相反。** 修法是 `&&` → `||`。

改成 `||` 之後仍保留「整張圖」那個退化情形：兩軸都貼齊 ⇒ 可動範圍是 0 ⇒ 框內拖曳**仍然**畫新框（否則開窗後在圖上拖曳會完全沒反應，那是 2026-10-06 修掉的舊缺陷）。

子代理逐行追出根因並**量到**決定性證據：`--wheel-payload <3 個 PDF>` ⇒ `status=Unsupported source=UNKNOWN targets=0 notice=不支援的格式 tools=0`，且 `--wheel-tool merge-pdf: not in the catalog []`。原因是 `FormatCatalog.Classify` 只在類別為 `IMAGE` 時回 `Ready`（`CodecRegistry.cs` 的註解自己寫明了這是刻意的），而 `ToolCatalog.ToolsFor` 對非 `Ready` 回空清單 ⇒ **`OpMergePdf` 的提交區塊在正式路徑上是死碼，`MergeUi.Open` 永遠不會被叫到**。

為什麼 S20.12 一直是綠的：**`--tools-list` 根本不吃 `--wheel-payload`**，它自己塞一個 `Ready` 的 `sourceFormat` 進去就結束 ⇒ 那是**目錄過濾查詢**的答案，繞過了 `Classify`；而「目錄查詢說有 merge-pdf」不等於「執行期拿得到工具」。

**教訓（已寫進碼與本日誌）：查得到的東西與跑得到的事情要分別斷言。一條查詢型斷言不能代替執行期斷言。** 子代理的注入演練把這件事證死了：**把 (b) 拿掉 ⇒ 只有 S21.07／S21.10／S21.11／S21.13 變紅，而 S21.01（目錄查詢）與 S21.02–06（視窗自測）全綠**——舊斷言看不到這個缺陷。

### (b) 的內容與護欄

`FormatCatalog.cs` 新增 `ToolFormats = { "PDF" }` 與 `HasApplicableTool()`，把「**有工具適用**」與「**可轉成圖片**」正式分成兩個判定；`TargetsFor` 對不能轉成圖片的來源回空清單。

- 修前：`status=Unsupported source=UNKNOWN targets=0 tools=0`
- 修後：`status=Ready source=PDF targets=0 layer=tool tools=6`（**格式層仍是空的**，不能把 PDF 轉成 PNG）
- 護欄仍在：`--convert <pdf> --to png` ⇒ **exit=9**、`error=Unsupported`、**0 個新檔**；`verify-m1d.ps1` 的 S12.8a/b/c 維持綠。
- 混合 payload 實測：`[jpg + pdf]` ⇒ `status=Mixed`、`tools=0`、notice「混合選取，請選同類別」⇒ 判定為**正確行為**（兩者沒有共同的可執行語意），照實斷言下來。

**子代理主動更正了我指定的做法，我接受**：我要求斷言 `--wheel-payload <pdfs> --tools-list` 必須列出 merge-pdf，但 `--tools-list` 原本完全不吃 `--wheel-payload`（那正是 S20.12 的問題本身）。它把 `--tools-list` 改成「**有酬載就用酬載走 `Classify`**，只有 `--wheel-source` 才是目錄查詢」，否則我指定的命令仍然只是目錄查詢。

## 2026-10-14 CUTOUT 顏色修正：產物是**去背成品**，不是遮罩

### 這一刀交付了什麼

**`d93296c`**（2 檔、+158／−3）：`ConversionEngine.cs`（+88／−2，新增 `RestoreSourceColours` ＋ 管線註解 ＋ 兩行日誌／訊息措辭）、`verify-m3d.ps1`（+70／−1，新增 **S22.23**、`Expect 22 → 23`，m3d 共 **108** 條）。

### 使用者怎麼發現的（一句話，而且他是對的）

原話：**「去背不是應該把背景去掉留人像或主物件嗎？為何現在的 cutout 功能是做出一張 alpha 遮罩圖？」**

他是在**成品上**一眼看出來的——不是看程式碼，也不是看我的報告。而那個成品確實是一張白剪影。

### 根因（程式碼上的因果鏈，不是猜測）

1. `RemoveBgModel.MaskToGrayFrame`：把模型的遮罩值**灌進 B／G／R／A 四個通道**（這是刻意的——下一步要放大，四通道同值才能讓任何 alpha 加權的重取樣算出同一個結果）。
2. `ConversionEngine.ExpandMaskToAlpha`：`pixels[p+3] = pixels[p+2]`，**只把 R 抄進 A**。
3. 然後**這份緩衝區直接交給 `EncodeBgraPng` 寫檔**。

⇒ 這條管線從頭到尾**沒有任何一步把來源的顏色放回去**。透明背景（A=0）是對的、半透明毛髮（0<A<255）也是對的，**錯的是主體的顏色**——輸出的 RGB 就是遮罩本身的灰值。

實測（1920×1281 狗毛照，引擎自己的日誌）：**209,794／209,920 px（99.94%）**在主體做完時 B／G／R 還是遮罩值。修前該來源輸出 **37,595 B**、修後 **403,353 B**（顏色真的裝進去了）。

### 為什麼整套驗收（107 條）完全沒抓到

**S22.05–S22.22 全部只量 alpha**：band、過渡帶、柔毛保留率、GridLock、specks／holes——沒有一條看過 B／G／R。而我給視覺模型看的對照圖，是**壓平到背景上的合成圖**：一壓平，RGB 本來就是灰的，看起來依然「乾淨」。⇒ 這是今天早上那次「拿壓平合成圖量 alpha」的**同一個錯誤家族**：**alpha 對 ≠ 成品對**。

### 修法與兩條守則

在精修之後、寫檔之前，新增 `RestoreSourceColours`：把**來源畫格**（模型看到的那一張，EXIF 方向已烤進像素）的 B／G／R 逐點放回，**alpha 一個位元組都不動**。

- ⚠ **逐像素對齊是契約，不是巧合**：alpha 平面已經被放大回原尺寸，兩者是同一格網，不需要也不可以做任何重取樣；對不上就丟例外，不交出錯位的圖。
- ⚠ **刻意不做 premultiply**：PNG 存的是 straight alpha，先把顏色乘上 alpha 會讓半透明的毛髮合成到深色背景時出現**黑邊**——那正是這顆工具最該保留的東西。

**「alpha 對 ≠ 成品對」。** 一顆工具只要有一個輸出通道沒被斷言覆蓋，缺陷就能在 107 條綠燈下出貨；而**壓平合成圖**會把 RGB 的錯藏起來，讓視覺檢查也失效。⇒ 驗收要看**成品本身**，而且斷言要**直接比對它與來源的關係**，不是比對某個統計量。

也記下一條工具陷阱：**`edit` 工具會吃掉檔案的 UTF-8 BOM**，而含中文的 `.ps1` 少了 BOM 會被 PowerShell 5.1 以 CP950 讀 ⇒ 中文雙位元組吞掉後面的引號 ⇒ 語法錯誤**落在你根本沒改的那一行**（實測：改完 m3d 後 2885 行炸、補回 BOM 立刻乾淨）。改完含中文的 `.ps1` 一定要確認前 3 位元組是 `EF BB BF`。

## 2026-10-14（下午）「去背不夠乾淨」——量出來的真身，以及一個被我自己的模擬否決掉的修法

使用者看完 CUTOUT 的成品後說「感覺可以再去背去得乾淨一點」。這一節是那句話的追查。

### 一、先排除「假的不乾淨」

- 把成品合成到中性灰底並放大 2 倍讓視覺模型品管，它回報「左上角殘留大量美國國旗碎片、紅白藍散落灰底」。**這是幻覺**：量出來那個區域留下的顏色是 `(41,24,43)` **暗藍灰**，不是紅白藍；而整張成品用 alpha≥8 當門檻連通分量分析，**主體以外只有 1 座小島（196 px，位置 (52,43)，平均 alpha 27）**，8px 以下的一座都沒有。
- 右上角（太空梭區）殘留 **0.0%**；左下／右下角殘留 91.2%／65.8%，但那些像素的顏色是棕色／褐色 `(114,71,41)`／`(150,106,64)`——**那是兩隻狗本來就在那裡**，是主體不是殘留。
- ⇒ 人物照這張在結構上**已經是乾淨的**。使用者說的不乾淨，不在這張上。

### 二、換大圖，真身就出來了：過渡帶寬度

新增度量：對每個半透明像素，算「到最近實心像素」＋「到最近全透明像素」的距離和 ＝ **過渡帶寬度**（單位：像素）。

| 圖 | 過渡帶平均寬度 |
|---|---|
| 人物照 512×410（模型原生，無放大） | **6.7 px** |
| 狗毛照 1920×1281（遮罩由 512 放大 2.5 倍） | **43.3 px** |
| 同一張狗毛照精修關閉 | **64.0 px**（⇒ 精修確實有在做，收窄了 33%） |
| **把成品縮到 768×512 再量（純縮放對照組）** | **19.3 px** |

`43.3 ÷ 2.5 ≈ 17.3 ≈ 19.3` ⇒ **過渡帶寬度與縮放倍率成正比**。43 px 在 1920 寬的圖上是全寬的 2.2%，**那是一整圈肉眼可見的暈**。這才是「不乾淨」的真身，而且它可量、可重現。

### 三、三個便宜的修法，全部被量測否決

1. **加大引導濾波半徑**（`RadiusMax` 8 → 16 → 24，重建三次）：狗毛照輸出**逐項相同**（43.3 px、269,754 個半透明像素）。原因寫在 `EdgeRefine` 的註解裡——**半徑只管第一階段「對齊」，那一步本來就是把過渡帶抹寬**；真正收窄的是第二階段，而它的強度 `s = clamp(SharpenGain × 放大倍率, 1, 3)` 與半徑無關。**我掃了一個改不動結果的常數。**
2. **第二輪註解裡已經列過的三個替代方案**（對原始遮罩 unsharp／對濾波後 alpha unsharp／再加「遮罩自己有沒有跨越 0..1」的閘門）：過渡帶反而變成 23.76%／18.02–21.99%／22.58%，孤點暴增。原因同一個：**局部平均值本身帶著粗遮罩的階梯，放大它就是把它畫清楚。**
3. **我自己的新提案：「α 有沒有跟著影像走」的第二道閘門**。動機是真的——引導濾波算出的 `a = cov(I,α)/(var(I)+ε)` 正是「α 的邊是不是影像的邊」，而現行閘門只看 `var(I)`，所以一張**整格都是毛**的照片會被判成「到處都有細節」⇒ 閘門全關 ⇒ 收窄完全不發生。**離線模擬（不動產品）結果**：

   | 門檻 t | 判為「暈」（可收窄） | 判為「跟著影像」（不動） | 被推到全透明 | 過渡帶 |
   |---|---|---|---|---|
   | 0.02 | 64,958 | 204,796 | 28,066 | 31.0 px |
   | 0.05 | 134,888 | 134,866 | 57,779 | 22.7 px |
   | 0.10 | 196,478 | 73,276 | 80,665 | 17.1 px |
   | 0.20 | 247,353 | 22,401 | 95,986 | 10.8 px |

   數字很漂亮，**但兩群的平均 alpha 幾乎一樣（123 vs 125）** ⇒ 這個分類器**根本沒把毛髮和暈分開**，在滿版毛髮紋理上局部共變異數就是雜訊。而被推到全透明的 2.8 萬～9.6 萬像素，**正是那些低 alpha 的飛散毛髮**——就是 2026-10-08 第一輪被罵的那件事。**提案作廢。**
   （對照組人物照：≥0.20 佔 52.6%、被推到 0 的是 **0**——因為那裡真的有「暈 vs 主體」的差別。）

### 四、結論（硬的）

在紋理滿版的圖上，**靠事後收窄不可能同時做到「乾淨」與「留毛」**。今天第三次量到同一個結論。要同時做到，只能換一個**更銳利的遮罩來源**。

已查證的候選：**BiRefNet**（MIT，涵蓋程式碼與權重，可隨產品散布；512×512 fp16 ONNX 與現行模型同輸入尺寸，只需改正規化；多份比較都說它在**毛髮與細邊緣**上勝出——正是我們量到的最弱項）。代價是模型大小：現行 MODNet fp16 **12.9 MB**，BiRefNet 全量 fp16 **490 MB**（lite 版較小，精確大小尚未量到，HF API 回 401）。**這是產品決策，留給使用者拍板。**

### 五、這一節留下的工具

- `tools\cutout-diagnose.ps1`：吃一張圖，跑一次去背，印出來源／成品的尺寸、不透明／半透明／全透明像素數、**RGB 與來源不符的像素數**、貼著主體的半透明像素比例、遠處淡像素、連通分量、孤塊、內部破洞。
- `tools\follow-probe.cs`：量「α 有沒有跟著影像走」（`explained = |cov(I,α)|/sqrt(var(I)+ε)`）與過渡帶寬度，並可**離線模擬**收窄後果。用法：`Add-Type -Path tools\follow-probe.cs -ReferencedAssemblies System.Drawing` 後呼叫 `[FollowProbe]::Follow(圖, 成品, 8, 2.5)`。

### 六、我的教訓（第 ⑥ 條）

**改參數之前先讀那段中文註解。** 我花時間重建三次去掃 `RadiusMax`，而它管的是**另外一個階段**；答案就寫在 `EdgeRefine.cs` 第 100–160 行，連「掃過哪些值、量到什麼」都列好了。**註解裡的取捨曲線是資產，不是裝飾。**

以及第 ⑦ 條：**改產品之前先離線模擬。** 這次的提案在模擬裡就被否決了——如果直接寫進 `EdgeRefine.cs`，重建、跑套件、看圖，然後才發現它把毛吃光，那是又一次第一輪。

## 2026-10-14（傍晚）換上 BiRefNet：使用者的抱怨從頭到尾都是對的，而錯的是我的儀器

### 〇、決策

把前面那節的岔路交給使用者拍板，他選了**直接換 BiRefNet 全量 fp16（490 MB）**。這一節就是把它接上去、量它、並且記下**我在這一節裡錯了兩次**。

### 一、模型介面：**不要猜，讓模型自己說**

`RemoveBgModel` 原本把介面寫成常數（`InputName="input"`、`OutputName="output"`、短邊 512），而且註解還寫著「改模型就一定要改它們」。真的換模型的那一天，這句話就變成了一種**假的保證**——它讓人以為只要換字串，而真正要改的是前處理的每一格。

所以先在日誌裡加了 `DescribeIo`（每個輸入／輸出的**名字、型別、形狀**一行）。這一行的代價是五行，回報是**不用猜**：

```
remove-bg: model 'ModelBiRefNet_1024x1024_fp16.onnx' loaded in 4633 ms
  (inputs=1 [input_image:System.Single[1,3,1024,1024]]
   outputs=1 [output_image:System.Single[1,1,1024,1024]])
```

（同一行也量到了成本：**載入 4633–4977 ms**，而 MODNet 是 139–190 ms ⇒ session 快取在這個模型上比以前重要得多。）

### 二、四個必須改的格子，其中三個已經由模型回答了

| 格子 | MODNet | BiRefNet | 來源 |
|---|---|---|---|
| 輸入名 | `input` | `input_image` | 模型 metadata（讀出來的） |
| 輸出名 | `output` | `output_image` | 模型 metadata（讀出來的） |
| 張量形狀 | 短邊 512、動態 | **固定 1024×1024** | 模型 metadata（讀出來的） |
| 正規化 | `x/127.5 - 1` | **`(x/255 - mean)/std`，ImageNet** | **只有這個讀不出來**——它不在 ONNX 裡，在下載頁旁邊的 `preprocessor_config.json`（實抓：`rescale_factor=1/255`、`mean=[0.485,0.456,0.406]`、`std=[0.229,0.224,0.225]`） |
| 輸出 | 已在 [0,1] | **logits，要過 sigmoid** | **量出來的**：`max=15.218 > 1.5` ⇒ 過 sigmoid |

⇒ 實作上：`KindOf(session)` 用**輸入形狀**判種類（1024 方形 ⇒ BiRefNet；其餘 ⇒ MODNet），名字與形狀都從 session 讀，正規化與 sigmoid 按種類分流。**MODNet 那條路（含它的日誌字串）逐字不變**——驗收套件讀的就是那些欄位。

（同時修掉一個 ORT 的事實：`session.Run` 的多載簽章是 **(輸入, 輸出名)**，不是 (輸入名, 輸出名, 輸入)。）

### 三、**我錯在哪裡（兩次）**

**第一次錯：我把視覺模型的「國旗碎片」判成幻覺。**

我的理由是兩個數字：那塊區域留下的像素平均顏色 `(41,24,43)`（我讀成「暗藍灰」），以及「alpha≥8 的連通分量裡，主體以外只有 1 座 196 px 的小島」。兩個都**看不到那片殘留**，因為它**與主體相連**（貼在太空人手臂後面）——連通分量分析對「連著主體的背景」是瞎的，而區域平均又把主體一起平均進去了。

**第二次錯：我拿一張「沒有背景」的照片當成「去背不乾淨」的代表。**

那張 1920×1281 的「狗毛照」，我量到過渡帶 43.3 px、把它當成「大圖會有一圈暈」的證據。直到用 BiRefNet 跑它，得到 `mask min=0.9419 max=1.0000 mean=1.0000`（**幾乎全不透明**）——請視覺模型看原圖，答案是：「**沒有明確的主體與背景之分，這是同一種材質的特寫（白色長毛皮毛），無法區分主體與背景**」。⇒ **BiRefNet 回答「整張都是前景」是對的**，反倒是 MODNet 在那張圖上吐出 269,754 個半透明像素＝在不該去背的圖上硬去。**那個 43.3 px 的數字是真的，但把它當成「去背不乾淨」的代表是選錯了樣本。**

### 四、真正的證據：兩顆模型的直接差分

不看統計量，直接問「**MODNet 留著、而 BiRefNet 去掉的像素是什麼**」（人物照 512×410，alpha≥128 vs ≤8）：

```
5,272 px   來源平均顏色 =(102, 43, 59) ← 紅色     bbox=(62,2)-(138,409)
4×4 分布：  1662    0    0    0
             2251    0    0    0     ← 97% 集中在最左那一整條
               47  206    0    0
             1040   66    0    0
```

⇒ **那片殘留是真的，而且就是照片左邊那面美國國旗**（紅色 ✓、最左條 ✓）。反向對照（BiRefNet 留著、MODNet 去掉）只有 **292 px**、顏色中性、散在中間 ⇒ 新模型幾乎沒有誤刪。

⇒ **使用者的抱怨從頭到尾都是對的；錯的是我的兩個儀器。** 而這也是為什麼「去背乾不乾淨」在 107 條綠燈下出貨：**顏色檢查（S22.23）抓不到它**——那片殘留的顏色**與來源一致**（它本來就該是那個顏色），它不是顏色錯，它是**背景**。只有語意判斷（或換一顆模型）能看見它。

（兩者半透明像素「離 0 或 255 的平均距離」是 52.6／53.4 ⇒ 差別在**數量**變少，不是軟硬不同 ⇒ 邊緣是真的**收緊**了。）

視覺模型獨立判讀（白底 2× 的兩張圖）：「**第二張明顯勝出**——頭頂沒有霧狀殘影、肩膀輪廓緊實銳利、兩隻狗毛髮末端乾淨、國旗完全被移除乾淨。」

### 六、驗收：**202/202 全綠**

改動**只加了一條分支**，MODNet 那條路逐字未動，所以三套一起跑：

### 七、取得與散布

- **現況**：BiRefNet 是**選用**，不是預設。不帶 `--remove-bg-model` 時走的仍然是 MODNet，所以既有使用者與驗收套件一行都不受影響。**要不要讓它變成預設，是使用者的決定**（會改動 S22.14–S22.17 那幾條「預設模型」驗收的意義）。

### 八、我的教訓（第 ⑧、⑨ 條）

**⑧ 儀器會系統性地看不見某一類東西，而那一類往往就是使用者在抱怨的那一類。** 連通分量看不見「與主體相連的背景」；區域平均看不見「被主體稀釋的殘留」；顏色比對看不見「顏色正確但區塊錯誤」；而套件裡的 107 條全都在看**別的**。⇒ 換一顆模型**最強的用途不是取代舊的，而是拿它當**一把新的尺**：`A 留著、B 去掉的是什麼` 這個問法不需要 ground truth，卻直接指出了缺陷。

**⑨ 選樣本本身就是一種斷言。** 我把一張「沒有背景」的毛皮特寫當成「去背不乾淨」的代表，於是一整節的推論都在講一件不存在的事。⇒ 量一個症狀之前，先確認那張圖上**真的有那個症狀可言**（這一條的代價，是一個下午）。

## 2026-10-14（收工前）「有檔案就是預設」：把偏好順序寫進產品，並讓驗收跟著改口

### 〇、決定

把「BiRefNet 要不要變成預設」交給使用者拍板，他選了**「有檔案就是預設」**。這一節是把它做完、把它驗完、以及記下**我在這一節裡又弄壞了什麼**。

### 一、`ResolvePath` 從一個檔名變成一個**偏好順序**

```
<exe 資料夾>\models\ModelBiRefNet_1024x1024_fp16.onnx   ← 在，且長度正是 489,666,272 bytes ⇒ 用它
<exe 資料夾>\models\model_fp16.onnx                     ← 否則（MODNet）
```

**長度那道門是刻意的**：這顆 489.7 MB 的檔案只在下載**成功**時才存在，而一個下載到一半的大檔如果被選走，使用者會從「工具正常、只是邊緣軟」變成「工具直接說模型損壞」——那是更糟的狀態。長度對得上但解不開的檔案仍然走原本的**具名狀態** `ModelCorrupt`（exit 3、零檔案、訊息說出下一步）；連問都問不到（路徑過長／權限／磁碟消失）時吞掉例外走 MODNet，因為「問不到」的正確答案就是「用另一個」。

判準不是「檔案在不在」而是「長度對不對」，所以這裡**沒有**新增一種狀態、也沒有新增一種訊息——它只是把「哪一顆」這件事從**常數**變成**函式**。

### 二、驗收跟著改口（前提變了，斷言就必須變）

- **S22.14**：原本斷言「旁邊那顆就是 `model_fp16.onnx`」。改成斷言**偏好順序的結果**：有偏好模型就用它（且日誌要指出是哪一顆），沒有才退回 MODNet；「一個模型都沒有」那一支不變（`ModelUnavailable`、exit 3、零檔案）。跑哪一支會寫在 detail 裡。
- **S22.15**：原本「把副本裡的**那顆**模型刪掉」——現在**兩顆都要刪**，不然「這個副本沒有模型」這個前提就不成立，而檢查會變成裝飾。同時加驗「原資料夾的**兩顆**都沒被動到」。
- **S22.24（新）**：一個偏好順序，只有當使用者**看得出**自己拿到哪一顆才有價值。S22.14 讀的是 UI 那側**報出名稱**的那一行；這一條**不相信任何名稱**：同一個來源跑兩次（一次完全不帶參數、一次用 `--remove-bg-model` 指名 MODNet），**比對位元組**——
  - 偏好模型在 ⇒ 兩次必須**不同**（偏好改的是產品，不是日誌字串）；

### 這一刀真正的接縫

目標格式的唯一來源是 `CodecRegistry.OfferedOutputs`，第一層扇形由 `FormatCatalog.TargetsFor` 算，
所以**加一個格式，輪盤會自己長出來**（`FormatCatalog` 一行都不用改）。但 `CreateEncoder` 的回傳型別是
`BitmapEncoder`（WIC），而 PDF **不是** WIC 編碼器——它是一個放頁面與內嵌影像物件的容器。
硬塞進那個抽象，五個既有格式的編碼路徑就一起長出分支。⇒ 先例早就存在：`ConversionEngine.MergePdf`
（2026-10-07）就是一條「非 WIC 的生產者」，本刀照它的形狀再拉一條 `ToPdf`，寫檔契約一字不差
（`AtomicWriter` → `NamingPolicy` → 三次重試 → 同一組失敗分類）。

### 量到的（不是推論）

```
convert job: files=1 target=PDF quality=85 offered=[PNG,JPG,BMP,TIF,PDF]
to-pdf: real-512.png -> real-512.pdf (512x410 px, 384.05x307.54 pt at 96x96 dpi; one page; source untouched)
codec PDF: decode=no encode=yes :: … encode is probed: a 2x2 image round-tripped as a
           2653B one-page PDF of 1.50x1.50 pt (written, then read back through PdfReader)
merge-pdf inspect（產品自己的檢驗器讀回產物）: page=1 size=384.1x307.5 rotate=0 contents=64
產物 real-512.pdf 507361 bytes；來源 sha256 不變
verify-m1c.ps1 -Section S9：checks=20 pass=20 fail=0
建置：0 警告 0 錯誤
```

`384.05` 而不是 `384.00` 是**對的**：那張 PNG 自己報的 DPI 不是剛好 96，而我刻意用**來源的實際 DPI**
換算頁面尺寸（`pt = px × 72 / dpi`）——這樣「1000px @300dpi」印出來是 240pt 而不是 750pt，
而且這一條可以客觀斷言。

### 過程中真的抓到的東西（都是當場量到才知道的）

- **一份隱藏的第二擁有者**：`Program.cs:7188` 自己抄了一份 `string[] declared = { "PNG","JPG","WEBP","BMP","TIF" }`。
  PDF 一進宣告矩陣，那份複本立刻成為唯一說謊的地方，產品自己的自我檢查就 FAIL 了
  （`FAIL  offered [PNG,JPG,BMP,TIF,PDF] is a subset of the declared MVP matrix`），而 offered 完全正確。
  修法是**問唯一擁有者**（新增 `CodecRegistry.DeclaredOutputs`），不是把 PDF 也抄進去——抄進去只是把複本養大。
  ⚠ 計畫的 Change Necessity 漏了這一份複本；「格式知識只有一個擁有者」這句話在這個 repo 裡仍然有例外。
- **PowerShell 的續行是 backtick，不是 `+`**：我把一條斷言拆成三行、行尾用 `+` 串接，語法當場 6 個錯。
  C# 的規矩套過來就會壞。
- **here-string 的結束標記 `'@` 必須在行首**：我把它寫在行尾，於是那個 here-string 沒有結束，
