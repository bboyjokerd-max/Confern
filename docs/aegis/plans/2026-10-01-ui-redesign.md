## 2. 現況 UI 事實（改動前必須知道，全部已實測）

- 輪盤：直徑 **220 px**，扇區＝**排除原格式後**的可輸出格式（MVP 實際只有 PNG/JPG/BMP/TIF，所以多數情況是 **2–4 個扇區**）
- 視窗：**304×330**（220 輪盤＋42 px 邊界），位置＝游標 **+18/+18**，靠邊自動翻轉
- 選中：目前只做**外擴 6 px**（原版是外擴＋填色變深，見 §3）
- 進度藥丸：寬度**依文字量測**（下限 168 px）、高 54 px，2 秒淡出、失敗 5 秒
- 重畫驅動：`PostMessage` 執行緒計時器（`WM_APP_TICK`），現已穩定
- 技術：**原始 Win32 分層視窗 ＋ GDI+**（規格 D10）。**這台沒有 NuGet 快取 → 不可新增任何 PackageReference**
- 預算：首次顯示 < 100 ms（現 15–18 ms）、常駐 < 80 MB（現 44 MB）、不搶焦點、不擋桌面點擊
- 紅線：原檔絕不修改/刪除/移動；不靜默失敗；不留 `.tmp-*`

## 4. 玻璃技術路線（唯一可行路，附風險）

DWM 的亞克力／Mica **只對一般視窗生效**；我們的輪盤是 per-pixel alpha 分層視窗（畫面自己合成），系統材質沒有東西可畫。因此：

1. 用 `BitBlt` 把輪盤底下的螢幕區域抓成一張 bitmap（GDI，無新相依）
2. 自己做可分離 box blur（2–3 次）→ 當玻璃底材
3. 疊上深色薄罩、奶油色扇區、髮絲線、柔光暈，全部走 per-pixel alpha

**代價與風險**：玻璃是**快照**（背後變動不會更新）；抓螢幕在 DRM/安全桌面會失敗（需 fallback 成純色玻璃）；模糊與光暈的時間必須落在預算內。

**spike 驗收標準**（未達標就得改設計）：
- 抓螢幕＋模糊＋合成總計 **< 10 ms**（輪盤預算 100 ms，現用 15–18 ms）
- 常駐記憶體增幅 **< 5 MB**
- 產出一張 PNG（`docs/design/reference/spike-glass.png`）供人眼與視覺模型判斷「看起來像不像毛玻璃」
- 深色桌布與淺色桌布各測一次（可讀性）

### 4.1 spike 結果（2026-10-01，兩輪）

| 項目 | 結果 | 證據 |
|---|---|---|
| 時間 | **總計 16.663 ms 不通過**；但超標全在抓螢幕 | `tools/glass-spike/REPORT.md` |
| 應用可控部分（模糊＋合成） | **3.877 ms 通過** | 同上 |
| 記憶體 | **+0.38 MB 通過** | 同上 |
| 深色／淺色桌布可讀性（D 調色盤） | **兩端都通過**：白字/扇區 WCAG 11.8–15.6（深）／7.7–10.5（淺） | `docs/aegis/work/2026-10-01-glass-spike/91-round2-d-palette.md` |
| 薄罩下限 | **約 60 %**（最壞＝純白桌布）；D 的 `.80` 有餘裕 | 同上 §3 |

**關鍵發現（不可優化，是物理限制）**：`BitBlt` 抓 16×16 與抓 512×512 一樣貴（皆 ≈16.6 ms），
換四條 API 路徑全都一樣，連**只等合成器、不搬像素**的 `DwmFlush()` 本身就是 16.67 ms
＝ **60 Hz 的一個 vblank**。所以：**抓螢幕必須移出關鍵路徑**（拖曳開始時抓一次、非同步），
輪盤顯示時直接用已備好的點陣圖；**且必須保留純色 fallback**（DRM／安全桌面會抓不到）。

**實作紅線（`UpdateLayeredWindow` 的 alpha 語意）**：alpha < 255 的像素，**RGB 不可含背景**。
玻璃區＝alpha 255、把模糊與薄罩烘進 RGB；圓盤外的投影／光暈＝純圖層。
違反這條，薄罩會**無聲消失**（第一輪的圖就是這樣壞的，見 91 號文件 §1）。

## 5. 實作順序

1. **玻璃 spike**（本檔 §4 驗收標準）——整個方向都押在它上面，不通過就先改材質方案
2. 依 §3 事實定 **2–3 個視覺方向**，用 `visualize` 做**可在對話中點擊的原型**給使用者挑
3. 選定後才改 GDI+ 實作（`src/Sidecar/Visual/WheelPresenter.cs` 為主，`ProgressPresenter.cs` 對齊同一套視覺語言）
   → **2026-10-01 完成**（方向 D）。新增 `Visual/WheelDesign.cs`（權杖）、`Visual/GlassSurface.cs`（快照＋模糊）；
   幾何改為「輪盤本體釘在游標 +(18,18)、留白 42px 往外長」（順手修掉本體實際落在 +32 的規格偏差）；
   診斷新增 `--wheel-backdrop=screen|dark|light`、`--wheel-dump-raw`。
   詳細取捨見 `docs/aegis/work/2026-10-01-wheel-impl/{10-intent,20-checkpoint}.md`
4. 改完用**真實渲染 frame**（`--wheel-frame` dump）＋視覺模型核對，不靠感覺
   → 實際旗標是 `--wheel-dump`；**另加 `--wheel-dump-raw`（保留 alpha）**，因為扁平化的圖驗不出 alpha 紅線。
   逐項量測腳本：`docs/aegis/work/2026-10-01-wheel-impl/check-frame.ps1`（16/16 全過）；
   視覺模型只當旁證（本專案已多次記錄它會自相矛盾）
5. 回歸：`verify-m1a/m1b/m1c/m1d` 全綠；補上「失敗那行必須含中文原因」的自動斷言（見 §7）
   → 最終二進位：m1b **50/50**、m1c **20/20**、m1d **43/43**、m1a **39/40**。
   m1a 唯一的紅是 **S4.2**，經對照實驗證實**不是本次改動**：S4 用 `--raise` 啟動（與輪盤無關），
   而自 `159952a` 註冊 `IDropTarget` 之後，合成 OLE 拖放就不再送 `WM_DROPFILES`
   （同一支 DragSim 對 `125070a` 會送）。S4 的六項行為斷言（收到檔名、立即收起、來源檔未變）全過。
   `HitLayer` 的相反註解已就地更正。S4.2 這條斷言要怎麼改屬 M1a 切片，**待決**。
   證據：`docs/aegis/work/2026-10-01-wheel-impl/90-evidence.md` §6
